# Autofill設計見直し（draft時点）

## 現在の問題

拡張を開いてパスワードを入力した後、ユーザーが結果を確認できない。読み込みを完了したのか、処理中なのか、失敗したのかが分からず、ファイル選択の負担をなくす目的をまだ達成できていない。この状態で機能を増やさず、操作と状態管理の設計を見直す。

## 確認済みと未確認

- 手動ファイル読込による全項目版の実フォーム入力は、本人から成功報告を受けた。各値の正しさ・サーバー側受理をエージェントが確認したものではない。
- Native Messaging版では、専用Chromeプロファイルへの接続設定を修正後、本人にパスワードダイアログが表示された。本人は入力後に何も起きないと報告している。
- 解除・ファイル読込・取り出し・session保存・popup再表示のどこで止まるかは未確認。popupが閉じたことやOSダイアログだけを原因と断定しない。
- 自動テストはブラウザからのnative接続と暗号化DMG操作をそれぞれ確認しているが、実際のOSパスワードダイアログから同じChrome画面に戻る一連の本人操作を確認していない。

## 見直しで決めること

1. **操作場所**: フォーカスが移ると閉じるpopupを主画面にするか、処理中も残る拡張タブ・サイドパネル等にするか。方式は未決定。
2. **状態の表示**: 未読込、解除待ち、読込中、取り出し中、読込済み、キャンセル、失敗を一つの流れで表示する。完了は読込・取り出し・session保存を確認してから示す。
3. **復帰と再試行**: popupを閉じた場合、別タブへの移動、キャンセル、パスワード違い、helper切断、タイムアウト、強制終了後のmount/lock残存に対する復帰方法を定義する。
4. **画面の整理**: 通常利用に手動YAML選択、ローカル模擬フォーム用の入力欄・保存操作、開発用の説明を並べる必要性を見直す。
5. **接続先と診断**: 通常Chromeと専用user-dataディレクトリを区別して登録・疎通を確認する。診断は固定の処理段階・成功失敗コードだけとし、値・パスワード・生の例外・申込URLを収集しない。

## 再開時の完了条件

- 本人がファイルを指定せず、拡張を開いてパスワードを入力するだけで、結果を同じ操作の流れで確認できる。
- 本人の管理下で実際のChrome・OSダイアログを通し、読込成功と保管庫の取り出しを確認する。値の保存・閲覧・ログ出力を検証手段にしない。
- キャンセル・失敗・再試行でも状態が不明にならず、別画面で削除した情報が復活しない。
- 個人情報をGit・通常ファイル・ログへ残さず、既存の暗号化保管庫とtrusted sessionの境界を維持する。
- フォームへの入力は明示操作とし、申込送信・カード承諾は引き続き自動化しない。

この文書は未決定事項の整理であり、新しい方式の実装や申込送信を承認するものではない。
