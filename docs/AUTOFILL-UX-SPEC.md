# Autofill UI/UX 正式仕様（Phase 1 確定）

- 決定日: 2026-10-10
- 対象: US Amex Business Platinum 申込フォームに対するChrome拡張
- Parent Epic: [#9](https://github.com/Masakazoo/us-amex-offer-hunter/issues/9)
- 既存実装の参照元: [Draft PR #8](https://github.com/Masakazoo/us-amex-offer-hunter/pull/8)（**一括マージしない**）
- この文書はUI/UXの合意済み仕様。技術的実現性・暗号強度・Chromeのセッション寿命は[#10](https://github.com/Masakazoo/us-amex-offer-hunter/issues/10)で検証し、仕様上の制約が判明したときのみ明示的に再相談する。

## 1. 目標と原則

**最初に一度だけ申込情報を登録。以後は対象申込フォームを開いて拡張を起動し、未解除ならパスワードを入力し、自動入力ボタンで入力する。** 最後の申込確認と送信は常に人間が行う。

1. 通常のユーザー画面は「小さなPopup」と「フルサイズのプロフィール設定タブ」の2つだけ。
2. **マスターパスワードは必須**。パスワードなし運用や平文プロフィールの永続化モードは提供しない。
3. **永続プロフィールは端末内で暗号化保存**。解錠後の状態をChrome終了まで保持するオプションは既定ON。OFFならその回の入力後にロックする。技術的な厳密な寿命は検証して定義する。
4. 入力フォームの対象判定は自動。通常UIに「フォームを検出」という追加ボタンを置かない。
5. **自動入力自体は明示的な「自動入力」クリックが必要**。ロック解除のみ・ページ検出のみで勝手に入力しない。
6. 必要以上に厳重な外部保管庫・ターミナル操作は持ち込まないが、SSN/Tax ID/生年月日等を扱うためパスワード暗号化は省略しない。
7. 暗号文・プロファイルをクラウドや外部APIへ送らない。Chrome sync不使用。Offer Lab観測データとは完全分離する。

## 2. 画面と状態

### A. Popup（通常利用）

必要最小限の構成:
- ヘッダー：Amex Autofill / 対応カード名 / 設定アイコン
- 対応フォーム自動判定の結果
- プロフィール状態（未登録 / ロック中 / 解除済み）
- 主CTA（状態に応じてパスワード入力・ロック解除・自動入力）
- 入力進捗・結果のサマリーと要確認の詳細
- 手動ロック、設定への導線

| 状態 | 主表示・主操作 | 注意 |
|---|---|---|
| 初回・未登録 | 「プロフィールを登録」→設定タブ | 実行ボタンなし |
| 対象外ページ | 「対応するAmex申込ページで使用してください」 | 認証後も自動入力なし |
| 対象ページ・ロック中 | パスワード欄、保持チェック、**ロック解除** | 解除だけで入力しない |
| 対象ページ・解除済み | **自動入力**、手動ロック | 申込送信はしない |
| 実行中 | 入力/選択/検証中の進捗 | 重複実行禁止。Popupを閉じても処理/結果が壊れない |
| 完了/一部失敗 | 件数の集計、要確認項目の展開、「再実行」 | 再実行は入力前の安全検査を繰り返す |
| エラー/キャンセル | 固定の原因分類＋回復操作 | 秘密や生の例外を表示しない |

Popupを開いたときに現在のタブのorigin/pathを自動検出。未対応なら入力を許さない。対象ページに途中で移動/更新した場合は判定をやり直す。

### B. 設定タブ（初回登録・編集）

- 初回はウィザードまたはタブ形式の4区分：**事業情報 / 個人情報 / カード設定 / セキュリティ**。
- 日本語を主ラベル、実Amexの英語表示名を併記（例：名（First Name）、事業形態（Company Structure））。英語名は実測されたものだけを確定扱いし、未確認は明示する。
- 必須/任意、入力例、形式エラー、条件付きの表示/非表示、未保存の変更を表示。
- DBAなし・個人事業主・自宅住所と事業住所が同一などの条件分岐を実装。
- SSN・Tax ID等はマスクし、必要時だけ本人が表示切替できる。
- 初回保存時にマスターパスワード作成・確認を必須にする。通常時は解除して編集。保存/パスワード変更/全削除を提供。
- パスワード紛失時は復旧できない。**確認後に全データを初期化して再登録**（復旧用バックドアなし）。

保存が成功したかを明確に表示。途中失敗では既存の暗号化データを不用意に上書き・破棄しない。

## 3. ユーザーフロー（画面遷移契約）

### 初回
1. 拡張を開く → 「プロフィールを登録」
2. 設定タブで申込情報を登録（現行PR #8の全項目定義を基本とし、実フォームのラベル/選択肢と照合する）
3. マスターパスワードを設定 → 暗号化して端末内保存 → 「保存済み」
4. 対象ページでPopupを開き自動検出 → 未解除ならパスワードで解除 → 「自動入力」

### 2回目以降
1. 対応する申込ページを開く → 拡張アイコンを押す
2. 拡張がページを自動検出。保持状態が有効ならパスワード欄を省略、そうでなければ入力して「ロック解除」
3. 本人が「自動入力」を押す
4. 自動入力＋項目検証 → 「入力済み / 一致済み / 条件により不要 / 要確認 / 失敗」等の件数と項目名のみ表示
5. 本人がAmex画面で全内容を確認し、自身の判断で申込操作を行う

**「自動入力」を押した直後の状態を確実に追跡**する。Popupの閉鎖/フォーカス移動に依存しない処理オーナーを用意する。

## 4. 入力結果の表現

- 入力済み：値を設定し、画面で確認できた（申込受理を意味しない）
- 一致済み：既存値が期待値と一致し、変更しなかった
- 条件により不要：DBAなし・住所同一等で非対象
- 未表示：条件/段階によって対象項目がまだDOM上にない
- 要確認：住所候補など曖昧、検証保留
- 失敗：DOM変化、無効、入力エラー、対象違い等

ポップアップの初期表示は「成功 x、既存値一致 y、要確認 z、失敗 w」の集計。詳細は折り畳みで固定項目名と原因コードのみ表示。値そのもの・生URL・個人情報・トークンは表示/ログ保存しない。

## 5. 暗号化・ロック・データ境界

- 認証付き暗号化（例：AES-GCM）とパスワードKDFを使う。**具体的なKDF/パラメータ/鍵保持方式は#10で安全性・性能を検証して確定**。
- `chrome.storage.local` には暗号文と復号に必要な非秘密メタデータだけ。鍵・平文・パスワードは永続保存しない。sync/外部送信なし。
- セッション用保持は `chrome.storage.session` 等の仕様を実機確認の上利用する。保持OFFなら入力実行終了時にロック。保持ONでも「Chrome終了まで必ず残る」と未検証の保証をしない。
- 手動ロック、Chrome再起動、拡張更新、worker再起動、複数ウィンドウ、保存失敗、誤PW、破損データの期待動作をテストする。
- Profile（本人PII）とOffer Lab（非PII Observation）を分離。個人情報や鍵をIssue/PR/テスト/ログ/HARに記録しない。

## 6. Autofill安全契約（PR #8の成果を再利用）

- 公式の確認済みhost/pathだけを対象とし、tab/document/URLと実DOMを**実行直前に再検証**。
- 一意なfield検出、既存値保持、ラベル/種別・可視・無効判定、条件分岐、select/radio/住所候補、再描画耐性、入力後の確認を維持。
- 申込送信、Accept、規約同意、CAPTCHA、隠しAPI実行は禁止。
- input/change等を起こした際、Amexページ自身が通信する場合があるため「ネットワーク送信ゼロ」と誤記しない。
- 自動検出と自動Popup表示は別機能。**ページを開いただけで入力はしない**。自動Popupは任意の後続Spike #15。
